# データベース設計

開発環境は Prisma 6 と SQLite。日時は UTC で保存し、画面・集計日は Asia/Tokyo で解釈する。1 枠は原則 35 分。実際の項目・制約は `prisma/schema.prisma` を正とする。

| テーブル        | 役割・主要項目                                                                        | 主な制約                                                           |
| --------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| User            | 内部 ID、メール、氏名、ロール、scrypt パスワードハッシュ、有効状態                    | メール一意                                                         |
| StudentIdentity | 内部 ID と学籍番号のダイジェストの対応                                                | User と 1 対 1、ダイジェスト一意。平文学籍番号をカルテに保存しない |
| Session         | セッショントークンのハッシュ、CSRF トークン、期限                                     | トークンハッシュ一意、User 参照                                    |
| TaProfile       | 対応科目、関連分野、単元、在室状態                                                    | User と 1 対 1。配列は JSON 文字列                                 |
| Course / Unit   | 授業、分野、単元、有効状態                                                            | 単元は授業を参照                                                   |
| Slot            | 公開勤務枠、TA、開始・終了、占有予約 ID                                               | 占有予約 ID 一意、TA・日時索引                                     |
| Booking         | 学生・担当 TA、授業、単元、質問、日時、状態、確認状態、来室・開始・完了日時、準備状況 | 学生・日時、TA・日時索引。枠の占有をトランザクション内で確保       |
| LearningRecord  | 予約、指導内容、理解、未解決、引き継ぎ、有効指導分数                                  | 予約 1 件にカルテ 1 件。予約参照、学生索引                         |
| Survey          | 任意回答、満足度 1～5、解決、対応可否、再利用意向、自由記述                           | 予約 1 件に回答 1 件、予約参照                                     |
| Notification    | 宛先、対象予約、本文、確認済みフラグ                                                  | 宛先・確認状態索引                                                 |
| HistoryGrant    | 学生単位のカルテ閲覧許可、許可者                                                      | 学生・閲覧者の組が一意                                             |
| Interview       | 調査日、対象区分、質問、回答原文、運営方法と理由、課題、改善案、引用許可、検証状態    | 原文を保持。実際の発言は初期登録しない                             |
| BookingAttempt  | 予約操作の成功・失敗、学生、時刻                                                      | 予約成立率の分母を記録                                             |
| Setting         | 管理者が入力する目標・導入前指標                                                      | キー一意。初期値は空で未取得                                       |
| AuditEvent      | 操作者、操作、対象 ID、時刻                                                           | 質問・発言・学籍番号本文を記録しない                               |
| LoginThrottle   | ログイン試行制限のカウンターと期間                                                    | 制限キー一意                                                       |

予約・カルテ・アンケート・ヒアリング・予約試行には `dataKind` を持たせ、DEMO と REAL を別々に集計する。デモ初期データはすべて DEMO。件数 0 と未取得は別の状態として扱う。

柔軟なマッチングは、対応科目一致 → レベル 1、関連分野一致 → レベル 2、それ以外 → レベル 3。レベル 2 は担当 TA の確認待ちとして記録し、レベル 3 は自動割当しない。一般相談・教員への相談経路を残す。TA の能力順位を保存・表示するフィールドはない。

予約、枠の占有、通知、監査記録を同じトランザクションで更新する。同じ枠の同時予約は条件付き更新と一意制約で防ぐ。SQLite の競合は有限回リトライし、競合時は再選択を案内する。

学習履歴は学生本人、担当 TA、学生ごとの明示的閲覧許可のある職員、およびシステム管理者に絞る。教員には全件を自動で開放しない。システム管理者の全体閲覧権限は責任者に限定して付与する。パスワードハッシュ・セッション・学籍番号ダイジェストを DTO に含めない。メールを含むアカウント一覧は管理者に限る。

将来 PostgreSQL に移行する際は datasource provider と接続先だけを変更して本番投入しない。移行用マイグレーション、JSON 配列の型、関係・外部キー、タイムゾーン、行ロック・並列予約テスト、データ移送の検証を行う。現状は SQLite 検証用で、大学の出欠システムとの接続はない。
