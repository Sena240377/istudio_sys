# 保守・引き継ぎ・復旧

このアプリは既存予約サービスから独立した検証用プロトタイプ。実在学生の個人情報を入力する前に大学の承認、管理責任者、アクセス権、保存期間、同意・問い合わせ窓口、運用基準を確定する。既存の SimplyBook.me 等の設定・データは変更しない。

## 日常運用

1. Windows の Node.js 24 以上と pnpm を用い、README の起動手順を実行する。開発サーバーは 127.0.0.1 のみに公開する。
2. デモ環境は架空データ専用。初期パスワードを本番で使わない。大学承認後の本番化では SSO、HTTPS、秘密管理、監視、アカウント発行・失効、ネットワーク制御を別途整備する。
3. 予約の確認待ち、未確認通知、一般相談受付、在室状態、未記録カルテを担当者が確認する。学生の相談経路を専門科目で閉じない。
4. 失敗ログでは質問・カルテ・発言・セッションを出力しない。DB、バックアップ、CSV は公開フォルダーに置かず、アクセスできる職員を限定する。
5. `pnpm.cmd typecheck`、`pnpm.cmd build` と隔離 DB の統合テストを更新時に実行する。依存バージョンは lockfile を維持し、検証してから更新する。スキーマ・依存更新時はアプリを停止してから `db:generate` を実行する。実行中の Windows DLL を再生成しない。`db:push` は自動再生成を省くため、Client 生成を別途忘れずに行う。

## バックアップ

```powershell
Set-Location "C:\path\to\istudio"
pnpm.cmd backup
```

Node.js の SQLite online backup を使用するため WAL を含めて一貫したスナップショットを作成する。保存前後に `PRAGMA integrity_check` を実行する。既定の出力先は非公開の `backups/`。接続先は `.env` または `DATABASE_URL` の `file:` URL とし、prisma 配下の DB に限定する。保存先は `--out=backups/monthly` のようにプロジェクト内の非公開フォルダーのみ指定可能。認証情報を含むため、別媒体に暗号化して保管し、世代管理・保存期限・復元訓練を決める。単一 PC 内だけのコピーは機器故障への対策にならない。

## 復元

```powershell
# 1. サーバーを実行している端末で Ctrl+C。すべてのアプリ接続を停止。
# 2. 復元先 DB とバックアップファイルを確認。
pnpm.cmd restore --file=backups/istudio-YYYY-MM-DDTHH-mm-ss-sssZ.db --confirm --app-stopped --port=3000
# 3. 再起動してログイン・件数・予約・カルテ権限を確認。
pnpm.cmd dev
```

復元スクリプトは対象ポートが停止していること、SQLite の整合性・外部キー・主要テーブル、対象が prisma 内であることを確認する。現在の DB の排他ロック取得も確認し、置換前バックアップと旧ファイルを保持する。別ポートで起動していた場合は正しい `--port` を指定し、他のプロセスも止める。ポート検査は OS 全体の DB 接続検査を代替しない。復元先 DB がない初期構築では先に `db:push` を実行する。大学側の承認を伴う本番復元は責任者の判断で実施する。

復元失敗時はサーバーを停止したまま、エラーとファイルを保存し、`*.before-restore-*.db` から同じ手順で再復元する。DB ファイルを手作業で削除してから復元しない。バージョンの異なるスキーマは移行・検証してから使用する。

## 障害と切り戻し

1. このプロトタイプの新規受付を止め、既存予約システムの担当者に状況を共有する。承認された既存の受付方法を使用する。
2. このアプリの最後のバックアップ、障害ログ、障害時刻、受け付けた予約一覧を職員が保全する。実在学生情報の持ち出し先は大学規程に従う。
3. 既存サービスへ戻す場合、担当者が重複予約・一般相談・来室済み案件を照合する。自動同期・自動上書きはしない。学生連絡は大学が承認した連絡手段と担当者が行う。
4. アプリを停止し、原因を修正して隔離環境で再検証する。責任者が再開時刻と対象データを承認し、予約・カルテ権限・通知を確認して再開する。

## 本番化前の残課題

- 現行システムの設計理由、35 分枠・休憩・営業日・担当変更・無断欠席・キャンセル期限・教員の閲覧範囲を要ヒアリングとして確認する。
- 公開勤務枠は検証用の自動生成。実勤務シフト管理、休日、シフト承認、負荷配分は今後の実装。
- QR 専用の受付端末、IC 学生証、メール/SMS、大学 SSO、既存予約・出欠サービス連携は未実装。
- SQLite の単一ホスト検証から、PostgreSQL・マイグレーション・可用性・監視・定期バックアップ・アクセスログ・保存期限削除へ移行する。
- 学籍番号のダイジェストは分離の検証用。実運用では推測耐性のある HMAC 等と鍵管理を検討する。
- アカウント新規発行、招待、本人確認、パスワード再設定、卒業・異動時の自動失効は大学の運用に合わせて追加する。
- 学習記録の共有は最小範囲に限定し、自由記述に不要な個人情報を書かないよう運用説明を用意する。
